## 3. 스키마 매핑 방법

### 3.1 노드: M5 개체를 AuraDB 노드로 변환

M5의 각 개체 ID를 노드 식별에 사용하고, 개체 유형을 Neo4j 레이블로 표현했다. 다른 팀원과 같은 AuraDB를 사용하므로 이번 작업의 레이블에는 **`B_` 접두사**를 붙였다. 각 노드는 공통 레이블 `B_M6Entity`와 유형별 레이블을 함께 가진다.

| M5 개체 유형 | Neo4j 레이블 예시 | 뜻 |
| --- | --- | --- |
| `Company` | `B_Company` | 회사 |
| `Person` | `B_Person` | 인물 |
| `Brand` | `B_Brand` | 브랜드 |
| `Product` | `B_Product` | 제품 |
| `Event` | `B_Event` | 행사·사건 |
| `MetricObservation` | `B_MetricObservation` | 수치·기간 등을 담는 지표 관측값 |

이번 입력에서 실제로 쓰인 개체 유형은 **11개**다. 공통 레이블 `B_M6Entity`는 이 개체들을 이번 데이터셋으로 함께 조회하기 위한 레이블이다. 노드에는 `entity_id`, `name`, `dataset_id`, 입력 지문 등과 함께 원본 M5 노드 기록을 `m5_record_json`으로 보존한다. 조회에 사용할 수 있는 단일 속성은 별도로 꺼내고, 서로 충돌하는 값은 임의로 하나를 확정하지 않는다.

이번 코드의 노드 식별자는 **데이터셋 ID와 M5 개체 ID**를 결합해 만든다. 팀원의 같은 이름 노드를 자동으로 찾아 합치거나 삭제하지 않는다. 같은 데이터셋 ID와 식별자를 다른 작업에서 사용한다면 충돌할 수 있으므로 구분이 필요하다.

### 3.2 관계: 주장 노드 없이 개체끼리 직접 연결

M2와 사용자 결정에 따라 별도의 주장 노드 없이 다음과 같이 개체 사이에 직접 관계를 만든다.

> **회사 A** → **지분을 보유한다** → **회사 B**  
> 관계의 정보: 지분율 · 기준일 · 출처 · 원문 근거

| M2 서술어 | Neo4j 관계 유형 | 연결 예시 |
| --- | --- | --- |
| `OWNS_STAKE` | `B_OWNS_STAKE` | 회사·인물 → 지분을 보유한다 → 회사 |
| `HOLDS_POSITION` | `B_HOLDS_POSITION` | 인물 → 직책을 맡는다 → 회사·기관 |
| `PARTICIPATES_IN` | `B_PARTICIPATES_IN` | 회사·인물 등 → 행사에 참여한다 → 행사 |
| `PRODUCT_UNDER_BRAND` | `B_PRODUCT_UNDER_BRAND` | 제품 → 브랜드에 속한다 → 브랜드 |
| `REPORTS_METRIC` | `B_REPORTS_METRIC` | 회사·브랜드 등 → 지표가 기록되어 있다 → 지표 관측값 |

위 표는 주요 예시다. 이번 입력에서는 **11개 관계 유형**이 실제로 매핑됐다. 코드는 각 관계의 주어·목적어 유형이 M2의 허용 방향과 맞지 않으면 적재 전에 오류로 중단하도록 작성했다.

### 3.3 같은 관계의 여러 근거와 서로 다른 시점

관계가 다음 조건을 **모두 만족하면** 하나의 직접 관계로 묶는다.

- 주어 개체 ID가 같음
- 서술어가 같음
- 목적어 개체 ID가 같음
- 수치·단위·상태·날짜 등 **관계 속성 전체가 같음**

같은 관계를 서로 다른 기사에서 확인했다면 원본 관계 기록은 관계의 `sources_json`에 각각 보존한다. `source_count`는 그 관계에 담긴 **원본 근거 기록의 개수**이며, 서로 다른 URL의 개수라고 단정할 수 없다.

반대로 같은 회사 사이의 지분 관계라도 **기준일이나 지분율 등 관계 속성이 다르면 별도 관계**로 보존한다. 공시 관계에 연결된 주석은 `disclosure_notes_json`에도 보존한다. 이름이 같다는 이유로 서로 다른 회사·브랜드를 새로 합치거나, 기사에 없는 관계를 새로 추론하는 처리는 하지 않았다.

### 3.4 원문 근거를 관계에 기록한 모습

예를 들어 다음처럼 같은 관계에 기사 A와 기사 B가 근거로 연결될 수 있다.

> **아모레퍼시픽** → **행사·활동에 참여한다** → **행사**  
> 관계 속성: 출처 기록 A와 원문 근거 · 출처 기록 B와 원문 근거

Neo4j에 저장된 `sources_json`은 출처별 관계 기록을 담은 JSON 문자열이다. 기사 URL, 문서·청크 ID, 원문 인용, 원래 관계 ID와 검토 상태 등의 기존 기록을 추적할 수 있다. 실제 개별 사례의 의미와 시점이 맞는지는 M8에서 원문과 대조해야 한다.

### 4.3 실제 적재

AuraDB 접속 정보는 사용자의 `.env` 또는 환경 변수로 제공하고, 다음 명령으로 실제 적재를 실행했다.

```powershell
uv run .\load_m6.py
```

코드는 연결을 확인한 뒤 노드와 관계를 기본적으로 **최대 500건씩 나누어** 저장한다. 각 묶음이 처리될 때마다 `노드 500/...`, `관계 500/...`처럼 진행 상황을 출력한다. 마지막에는 DB에서 결과를 다시 읽어 매핑 결과와 비교한다.

**실제 실행 결과:**

```text
AuraDB 연결 성공
...
노드 12,247/12,247
관계 13,322/13,322
적재 결과 검증 성공: {"nodes": 12247, "relationships": 13322, "source_records": 17726}
```

위 `source_records`는 이 데이터셋의 관계에 담긴 **원본 근거 기록 수의 합**이다. 17,726개의 Neo4j 관계가 있다는 뜻은 아니다.

## 5. 재적재와 출처 유지 확인

### 5.1 같은 입력을 다시 실행하는 이유

프로젝트 요구사항에는 **재적재 시 중복 여부와 출처 정보 유지 확인**이 포함되어 있다. 이를 확인하기 위해 사용자는 최초 적재가 성공한 후 동일한 입력과 데이터셋 ID로 같은 명령을 한 번 더 실행했다.

```powershell
uv run .\load_m6.py
```

### 5.2 다시 실행해도 진행 건수가 표시되는 이유

이 코드는 기존 항목을 모두 건너뛰지 않는다. 같은 식별자를 기준으로 Neo4j의 `MERGE`를 사용해 기존 노드·관계를 다시 찾고 속성을 반영한다. 따라서 재실행 중에도 `노드 ...`, `관계 ...` 진행 숫자가 표시된다. **이 숫자는 해당 실행에서 처리한 건수이며 새로 생성된 건수를 의미하지 않는다.**

코드는 입력으로 만든 전체 매핑 결과의 지문을 보존한다. 기존 데이터셋에 다른 지문의 노드가 있으면 새로운 입력이 섞이지 않도록 중단하도록 작성했다. 최초 적재와 재적재 로그에 표시된 입력 지문의 앞부분은 모두 `305f574aca152a61`이었다.

### 5.3 재적재 후 확인한 결과

재실행 후에도 다음 결과가 출력되었다.

```text
적재 결과 검증 성공: {"nodes": 12247, "relationships": 13322, "source_records": 17726}
```

최초 실행과 건수가 같았고, 코드가 매핑 결과와 대조한 노드·관계의 ID와 유형, 양 끝의 방향, 매핑된 속성 및 관계별 출처 기록도 일치했다. 따라서 **이번 실행에 사용한 동일 입력과 `brian_m6_20261108_v1` 데이터셋 범위에서** 재적재로 노드·관계가 추가 중복되지 않고 출처가 유지됨을 확인했다.

매 실행 끝의 `같은 입력·dataset-id를 다시 실행할 때 중복 여부도 별도 검증하세요`는 일반 안내 문구다. 최초 적재 후 한 번 더 실행해 위 결과를 얻었으므로, 이 확인을 위해 같은 작업을 다시 반복할 필요는 없다.

### 5.4 중단할 때의 동작

노드와 관계는 여러 묶음으로 나뉘어 별도 트랜잭션으로 저장된다. 중간에 실패하거나 `Ctrl+C`로 중단하면 **이미 완료된 묶음은 남을 수 있다.** 같은 입력과 데이터셋으로 다시 실행할 수 있도록 구성했지만, 동시 실행은 피하고 최종 검증 결과를 확인한다. 최초 실행 시 생성한 노드 식별자 유일성 제약은 적재가 중단되더라도 남을 수 있다.

## 6. 실행 과정에서 확인한 문제와 해결

### 6.1 `uv add neo4j` 중 프로젝트 파일 누락

| 항목 | 내용 |
| --- | --- |
| 발생 시점 | Neo4j Python 패키지를 추가하려던 단계 |
| 출력된 오류 | `Expected a Python module at: ...\\src\\baik\\__init__.py` |
| 확인 내용 | 현재 `baik` 프로젝트가 빌드 시 기대하는 파일을 찾지 못함 |
| 수행한 조치 | 해당 위치에 빈 `__init__.py`를 만든 뒤 `uv sync` 실행 |
| 확인 결과 | `Built baik`가 출력되어 당시 프로젝트 빌드가 성공함 |

이 결과는 누락된 파일 때문에 발생한 당시 빌드 오류가 해결되었다는 뜻이다. 삭제된 원래 파일에 내용이 있었는지까지 확인하거나 복원한 것은 아니다. `neo4j`는 Python의 Neo4j 드라이버이고, `.env`를 읽는 패키지는 설치 시 `python-dotenv`, Python 코드에서는 `dotenv`라는 이름을 사용한다.

### 6.2 AuraDB 연결 시 `Unable to retrieve routing information`

| 항목 | 내용 |
| --- | --- |
| 발생 시점 | 매핑 확인 후 AuraDB에 연결하던 단계 |
| 출력된 오류 | `ServiceUnavailable: Unable to retrieve routing information` |
| 이번 조치 | 이전에 사용한 `certifi` 인증서 경로를 현재 PowerShell의 `SSL_CERT_FILE`에 설정한 뒤 다시 실행 |
| 확인 결과 | 이후 `AuraDB 연결 성공`이 출력되고 실제 적재가 진행됨 |

사용자가 실행한 인증서 경로 설정은 다음과 같다.

```powershell
$env:SSL_CERT_FILE = (uv run --with certifi python -c "import certifi; print(certifi.where())")
```

`SSL_CERT_FILE`은 인증서 파일 자체가 아니라 **파일 경로를 담는 현재 PowerShell의 환경 변수**다. `Installed 1 package`는 명령 실행에 필요한 `certifi` 패키지를 준비했다는 안내였다. 이 설정은 새 PowerShell 창이나 다른 환경에 자동으로 이어진다고 가정하지 않는다.

이번 오류의 최하위 예외 메시지는 이 실행 로그에서 별도로 확인하지 않았다. 따라서 **이번 오류가 반드시 인증서 문제였다고 확정할 수는 없지만**, 위 설정 후 재실행에서 연결이 성공한 것은 확인했다. 모든 사용자에게 같은 인증서 설정이 필요한 것은 아니다.

### 6.3 최초 적재 전 레이블·속성 경고

최초 실행에서 `B_M6Entity` 레이블과 `input_hash` 속성이 없다는 경고가 표시되었다. 이는 적재 전에 같은 데이터셋이 이미 있는지 조회할 때, 해당 레이블과 속성이 아직 데이터베이스에서 인식되지 않았다는 경고였다. 이후 노드·관계 적재와 최종 검증은 성공했다. 경고 메시지와 실제 적재 실패를 구분한다.

### 7.2 남은 한계

1. **잠정 정규화:** M5에서 규칙으로 연결했거나 개별 보존한 개체가 포함되어 있다. 적재 성공은 동일인·동일 제품·행사 회차가 모두 정확하다는 뜻이 아니다.
2. **지표와 시점:** 일부 지표에는 수치·단위가 없고, 일부 행사에는 연도 확인이 필요하다. 없는 정보를 임의로 채우지 않았다.
3. **추출·적재 범위:** M4 미처리 청크와 이번 M5에서 제외한 관계는 현재 데이터셋에 없다. 관계가 없다는 것만으로 실제 사실이 없다고 판단할 수 없다.
4. **재적재 검증 범위:** 확인한 것은 이번 동일 입력·동일 데이터셋의 재실행이다. 다른 입력 버전, 동시 실행 또는 모든 운영 환경에 대한 검증은 아니다.
5. **질문 답변 검증:** 노드와 관계가 저장됐다는 것과 핵심 질문의 답이 원문에 맞는 것은 다르다. M7에서 조회하고 M8에서 출처·시점과 함께 대조한다.
