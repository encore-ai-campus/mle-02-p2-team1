## 2. M8의 목적과 검증 범위

M8의 목적은 그래프에 연결된 정보가 **어떤 원문에서 왔는지**, 추출과 정규화 과정을 거치며 **의미와 방향이 유지됐는지** 확인하는 것이다.

예를 들어 다음 관계를 검증한다.

> 아모레퍼시픽홀딩스 → 지분을 보유한다 → 아모레퍼시픽

공시 원문에 실제로 두 회사와 지분율이 나오는지, 추출 단계에서 두 회사의 순서가 맞는지, 정규화 단계에서 다른 회사와 섞이지 않았는지, AuraDB에도 같은 관계와 출처가 저장됐는지 살펴본다.

### 2.1 검증 대상과 자료

| 자료 | 확인한 역할 |
| --- | --- |
| 수집 뉴스 원문 사본과 청크 | 기사의 내용, 청크 위치와 저장된 인용 확인 |
| 공시 보고서 및 재무 자료 | 회사, 지분율, 기준일, 재무 수치와 관련 주석 확인 |
| M4 추출 결과 | 원문에서 추출한 주어·관계·목적어와 속성·인용 확인 |
| M5 정규화 결과 | 원래 개체가 어떤 대표 개체 ID로 연결됐는지 확인 |
| M7 조회 자료 | 실제 AuraDB에서 조회한 경로와 관계 속성 확인 |
| M8 보완 후 실행 로그와 CSV | 교정본 대조 결과와 수정한 시상식 관계 확인 |

이번 검토는 **Brian이 적재한 데이터셋**을 기준으로 한다. 같은 AuraDB에 있는 다른 팀원의 데이터는 검증 대상으로 삼지 않았다.

### 2.2 사례를 선정한 기준

M7에서 조회한 CQ02·CQ04·CQ05·CQ06·CQ07·CQ08·CQ10의 원본 관계 기록 **16건**을 선정했다. 여기에 별도의 지분 관계 조회에서 `56% 이상`, `종류주 11.65%` 사례를 한 건씩 추가해 **총 18건**을 검토했다.

선정할 때 뉴스·공시·재무 자료가 포함되도록 하고, 지분·직책·브랜드·제품·행사·장소 및 여러 홉의 경로에서 오류가 생길 가능성이 있는 사례를 살펴보았다. 이 중 다수의 출처가 묶인 직접 관계는 **선택한 출처 기록**을 확인했으며, 모든 출처를 전수 검증하지는 않았다.

뉴스 14건은 확보한 원문 사본의 문자 구간과 M4 청크를 비교하고, 해당 인용이 청크 안에 있는지 확인했다. 기사 사이트에 접근할 수 없었던 사례도 있어, 수집 사본의 내용과 실제 웹에서 다시 확인한 내용을 구분했다. 2024년 연합뉴스의 시상식 사례는 확보한 텍스트가 **세 줄 요약**이므로 검토 범위도 그 요약으로 한정했다.

## 3. 검증 방법과 확인 기준

| 단계 | 확인한 내용 | 확인 예시 |
| --- | --- | --- |
| **원문** | 회사·인물·행사, 관계, 숫자·기간이 실제 문맥에 있는지 | 공시 표의 투자회사와 지분율 |
| **M4 추출** | 주어·관계·목적어의 의미와 방향, 인용 및 속성 | 투자회사와 피투자회사의 순서 |
| **M5 정규화** | 원래 표현이 올바른 개체 ID로 연결됐는지 | 같은 이름의 서로 다른 시상식을 잘못 합쳤는지 |
| **AuraDB 그래프** | 노드·관계·속성·출처가 조회 결과에 반영됐는지 | 지분율과 기준일, 근거 기록 조회 |

추가로 다음 항목을 점검했다.

- **방향:** 지분 보유 회사와 지분을 보유받는 회사가 바뀌지 않았는지 확인한다.
- **근거:** 관계의 원문 인용, 문서 ID·청크 ID·출처를 추적할 수 있는지 확인한다.
- **중복과 오병합:** 같은 표현을 가진 서로 다른 행사나 다른 시점의 지분 기록을 하나로 처리하지 않았는지 확인한다.
- **스키마와 적재 누락:** 입력과 매핑 결과의 유형·방향을 검사하고 교정본과 실제 DB의 노드·관계·출처를 비교한다. 이는 **교정본을 기준으로 한 형식·적재 대조**이며, 원문에서 추출되지 못한 모든 관계를 전수 확인한 것은 아니다.

## 5. 오류 보완 사례: 서로 다른 시상식의 오병합

### 5.1 발견한 문제와 발생 원인

여러 기사에서 LLM이 행사 이름을 구체적인 고유명 대신 `시상식`이라고 추출했다. 이때 행사 날짜가 구조화 속성에 들어 있지 않았고, M5에서 **같은 이름과 연도 미상**인 행사들을 유연한 규칙으로 하나의 개체에 연결했다.

하지만 원문 문맥을 확인하니 다음 세 행사는 서로 다른 행사였다.

| 실제 행사 | 원문 행사 언급 | 해당 원본 관계 기록 |
| --- | ---: | ---: |
| 2024 제주 그린어워드 시상식 | 2개 | 3건 |
| 2025 제주 그린어워드 시상식 | 1개 | 1건 |
| 한국광고학회 2026 올해의 브랜드상 시상식 | 7개 | 7건 |
| **합계** | **10개** | **11건** |

### 5.3 실제 AuraDB 적용과 전후 비교

사용자는 자신의 PC에서 사전 조회를 실행해 **변경 전 상태**를 확인했다. 그 후 `patch_m8.py --apply`를 실행했고, 프로그램은 수정 전 대상 데이터를 백업한 뒤 보완과 검증을 수행했다.

| 확인 항목 | 보완 전 | 보완 후 실제 확인 |
| --- | ---: | ---: |
| 노드 | 12,247개 | **12,249개** |
| 직접 관계 | 13,322개 | **13,322개** |
| 원본 근거 기록 | 17,726건 | **17,726건** |

하나의 행사 노드를 세 개로 바꾸어 노드는 2개 늘었고, 대상 관계 5개를 5개로 다시 연결해 직접 관계 수는 같았다. 관계의 원본 근거 기록도 17,726건으로 유지됐다.

사용자가 제공한 실행 결과:

```text

수정 전 백업 저장: ...\\m8_backup_20261108_231035_428889.json
```

### 5.5 수정 범위와 재실행 시 주의

수정 코드는 `brian_m6_20261108_v1` 데이터셋의 행사 노드 1개와 관련 관계 5개를 교체한다. 다른 팀원의 데이터셋은 변경 대상이 아니며, 예상 밖의 연결이 있으면 중단하도록 검사한다. 또한 교정된 입력을 식별하기 위해 이 데이터셋의 노드 **12,249개**와 관계 **13,322개**의 `input_hash`를 갱신한다. 수정 및 수정 후 대조는 하나의 트랜잭션으로 수행한다.

이후 M6 코드를 사용할 때는 원래 입력이 아닌 **`M5_after_M8.zip`**을 지정한다. 기존 원본 입력은 입력 지문이 달라 그대로 사용하면 중단되도록 설계됐다. 같은 데이터셋에 여러 적재·수정 코드를 동시에 실행하지 않는다.

### 7.2 실행한 주요 명령

```powershell
# DB를 변경하지 않고 현재 상태 확인
uv run .\patch_m8.py

# 사전 확인 성공 후 실제 보완
uv run .\patch_m8.py --apply

uv run .\load_m6.py --input .\M5_after_M8.zip --verify-only
```

위 명령 중 `--apply`는 **실제 DB를 변경**한다. 이 보고서는 이미 사용자가 실행한 결과를 기록하며, 같은 작업을 다시 실행해야 한다는 뜻은 아니다.

로컬에서는 보완 데이터와 코드에 대한 테스트 8개가 통과했다. 여기에는 DB를 흉내 낸 모의 테스트가 포함되며, 실제 AuraDB에서의 보완·검증은 사용자가 제공한 실행 로그와 CSV로 별도 확인했다.

### 한계

1. **전체 정확도 미산출:** 정답 라벨을 갖춘 대표 표본이 아니므로 검토 결과로 전체 정확도·오류율을 계산하지 않았다.
2. **전수 사실 검증 아님:** 17,726건의 근거 기록이 보존됐는지의 대조와, 그 기록 모두가 사실에 맞는지의 평가는 다르다. 이번에는 선정 사례를 확인했다.
